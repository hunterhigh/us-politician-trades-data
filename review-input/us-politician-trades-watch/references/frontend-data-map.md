# Frontend-to-data map

The renderer and question-answer path consume the same `politician-dashboard/v1` snapshot. The five canonical collections are the only inputs; every other number is rebuilt by `scripts/process_snapshot.py`.

| Dashboard module | Canonical input | Deterministic rule |
|---|---|---|
| Global 30/90-day switch | `transactions[]` | Filter by `transaction_date`, inclusive of the cutoff date; never filter recent trades by filing date. On the global Dashboard this control is a scroll anchor only: the priority cards are fixed at 30 days, while both the 30-day and the 90-day block render at once, each as its own table, and the 国会山买入共识 blocks below them render both windows too. The anchor reaches the tables only — it must never scroll to a consensus block, which is why those blocks carry `data-consensus-window` rather than the `data-window-block` the anchor resolves by first match. The person and ticker views keep it as a real filter |
| Masthead dock and anchor landing | — | The masthead (`position: sticky`, `z-index: 30`, below the person profile, security view, and drawer overlays) stays pinned for the whole scroll so the 30/90 control is reachable from anywhere, and compacts to `--dock-h` once a `.dock-sentinel` element above it leaves the viewport. Because it is in normal flow, compacting releases its height and shifts every block below it upward — 39px on desktop, up to 171px on a narrow screen. Three rules follow, and each fails silently. Its height and padding must stay out of the `transition`: the compaction has to land in the frame it is applied, or anything measuring a landing point catches a half-compacted layout. The anchor must measure the target's document position with the bar already compact, then scroll to `position − bar height − ANCHOR_CLEARANCE`; an unadjusted `scrollIntoView` under-scrolls and leaves the window heading behind the bar, and a correction issued after the fact is discarded because the smooth scroll is still in flight. The scroll-spy threshold that decides which of 30/90 is lit must be derived from that same `ANCHOR_CLEARANCE` with a few pixels of margin, never chosen independently: the landing parks the block exactly at the clearance, so a threshold set above it lights 30 while the reader is looking at the 90-day block. Hold the highlight until the scroll settles rather than for a fixed delay — these jumps take 1.4–1.6s. Give `.segmented button` `white-space: nowrap`: the `30 天` label contains a space, and a compacted bar squeezes the buttons first, so they wrap, and the bar regrows by exactly what the compaction saved |
| Window block heading | filtered `transactions[]` | Every 30-day and 90-day block is a separate bordered table, and its `30 天窗口` / `90 天窗口` heading stands above that table, outside its border, left-aligned to the table's outer edge — the heading labels the table rather than being the table's first row, so the reader sees "heading, then table" and the two tables read as two tables. Render it as a full-size serif heading in the text colour, not as a small accent-coloured tag: a reader scrolled into the middle of a block identifies its window from the heading, not by scrolling back to the switch, and a low-contrast tag is unreadable exactly when it is needed. Keep it neutral rather than signal-coloured, for the same reason the card rank chips are: an accent colour here competes with the green buy and red sell encodings |
| Per-block view switch | — | Each of the two blocks carries its own `国会山热门关注股票` / `标的交易明细` switch bar as the table's first row, directly under the window heading. The two bars mirror one shared view state and are always switched together, so the two windows on screen never show different views at once; the switch is not duplicated per block as independent state. The two filter controls inside the transaction view *are* per block: each table owns its own search text, direction filter, and instrument filter, and changing one re-renders only that table. Keep those two facts together — a single shared filter would bind both tables to one query, and an unsynced view switch would put the 30-day block on hot stocks while the 90-day block showed transactions |
| Board-wide metrics | — | The global Dashboard renders no board-wide metric strip: the priority-card grid is the first module under the masthead. Counts such as active people, buy/sell totals, and aggregate amount are shown only on the surfaces that give them a subject — the person profile (record count, owner split, instrument split) and the security view (unique officials, amount range). Do not reintroduce a Dashboard total, or a person-profile metric strip, that has no person or ticker attached |
| Active people | filtered `transactions[]` | Unique `person_id` count. Shown per ticker on the security view and per person on the profile; never as a board-wide Dashboard total |
| Buy/sell disclosure count and red/green bar | filtered `transactions[]` | Count transaction rows by `transaction_type`; do not amount-weight the bar. Rendered on the security view's direction bar and on the person profile's direction filter buttons; the person profile has no split bar of its own, because the same bar already sits on every security view the person's trades lead to, and the record count is stated in the trade table's own head. Not on the Dashboard. Draw each bar as a pill track, not as two abutting colour blocks: the track is fully rounded (`border-radius: 999px`) on a white ground with an inset hairline, each segment is fully rounded in its own right, and a 3px gap is left between them. Two colours placed directly against each other read as one gradient across the join, so the white gap is what makes two blocks legible as two blocks — which is also why the track is white rather than grey, since a grey ground shows through the gap instead of the bright seam the reference has. The track is never clipped (`overflow: hidden` is deliberately absent): the segments already round their own corners and inset 2px, so nothing needs clipping, while clipping would swallow both the hover lift (`scaleY(1.25)`, 8px to 10px) and the `:focus-visible` outline drawn at `outline-offset: 3px` outside the track — and a focus ring a keyboard user cannot see is a focus ring that does not exist. Render no percentage beside the bar: the reference's percentage labels were explicitly not wanted, and the bar encodes the disclosure count alone, not a share |
| Aggregate disclosed amount | filtered `transactions[]` | Sum `amount_low` and `amount_high` independently. Rendered on the security view's summary strip; the person profile carries it per record in the trade table's 金额 column rather than as one person-level total, which would read as a position size |
| Median disclosure lag | filtered `transactions[]` | Calendar days from `transaction_date` to `filed_at`; this is observed lag, not a lateness ruling. Rendered per record as the 滞后 column of the person trade table and per row on the security view, not as a person-level metric |
| Person timeline | `people[]` + filtered `transactions[]` | Join only on stable `person_id`; preserve disclosed owner and official evidence fields |
| Priority-person cards | `people[].priority` + filtered `transactions[]` | Data-first cards in a fixed 30-day window, three per row. Each card holds exactly two direction cards, laid out side by side as left/right vertical rounded rectangles — purchase on the left, sale on the right, always in that order, equal width, equal height, stretched to the taller one, so an empty direction never collapses the pair. Side-by-side rather than stacked is what makes the two directions comparable at a glance: stacked bands read as two segments of one column, and the direction encoding degrades to reading a single character. Each direction card lists every ticker that direction traded in the window as chips, ordered by summed `amount_high` descending, then summed `amount_low`, then record count, then ticker ascending, and capped at three chips with the remainder folded into a `+N` chip — so the first chip is still the largest position without that one position owning the whole row. Inside a direction card everything stacks vertically, because each one is only half a card wide: a header row carrying the direction swatch beside the ticker count and record count, then the chip row, then the two dates on their own lines. Name, position, and a small inline portrait are supporting detail, not the visual focus. Amounts are deliberately absent from the card: each chip carries its range in a hover tooltip, and the `+N` chip's tooltip lists every folded ticker with its range, one per line. Folding may reduce how many chips are visible at once but must never make a disclosed amount unreachable. Fill the chip solidly — a pale character on a pale square is not a readable direction encoding — keep the direction card's body text neutral, and tint each card with its direction's wash edged in its colour. A direction with no records keeps its card and its swatch and goes neutral, so the card's skeleton never collapses and the swatch still reports which direction is empty; only the card's wash and edge change, never the swatch's. Because the card labels are only “买入 / 卖出” (shortened to a single 买 / 卖 character inside the chip) and it carries no ranking adjective, the ordering rule is documented here instead of on the card: it is by summed disclosed amount, never by record count, and it describes a ranked disclosure statistic, not a recommendation, score, or trading signal. The card must never say “最多买入 / 最多卖出”. The tooltip is a mouse-only affordance and must stay pure CSS: the grid is rebuilt through `innerHTML` on every re-render, so any bound listener would be discarded — and a click listener bound to a chip would be lost the same way, which is why chip clicks ride the board's delegated `data-ticker-link` handler instead. The card's root element is an `<article>`, never a whole-card `<button>`, because the card now holds two destinations: each ticker chip is a real `<button>` carrying `data-ticker-link` that opens the security view, and the name is a real `<button>` carrying `data-person-link` that opens the person profile. Button-in-button is illegal nesting, so a card that is itself a button could not offer either. The two destinations are dispatched by the capture-phase delegated handlers, which run before the card's own click listener and stop propagation, so one click can never jump two levels; the card's listener is the fallback for a click on the card's empty area and opens the person profile. Do not add `tabindex` to anything here — every clickable element is already a real button. Its containing block is the chip row, not the individual chip, and its width is capped at that row's width: a chip can sit 150px into a column that is only ~210px wide, while an amount range is itself over 100px, so a tooltip anchored to the chip and left-aligned necessarily spills into the neighbouring direction card and covers its counts. Do not restore `position: relative` on the chip — it silently re-anchors the tooltip and voids the width cap. The tooltip keeps its content width when it fits, wraps when it does not, and may break an over-long amount range as a last resort rather than leave white text outside its own dark background. That keeps the card's `aria-label`, which sits on the name button, the summary a screen reader hears first: it must speak every chip actually rendered (ticker and range), add a total count when the list was truncated, and carry both directions' record counts, trade dates, and filing dates. Each chip additionally carries its own `aria-label` with its range, because a keyboard user reaches the chip directly and a hover-only tooltip is unreachable for them. The `+N` chip has no destination — it stands for several folded tickers, not one code — so it stays a non-interactive `<span>` and keeps the `help` cursor that marks "there is more here", while the clickable chips take the `pointer` cursor. Lead the date line with “N 笔” only when it aggregates more than one record — a single-record range carries no count, and an aggregated range must not read as one trade. The date line is direction-level and leads with 最新, because once a direction lists several tickers no single ticker's date represents the line; its representative record is the latest `transaction_date` in the window with ties broken by `filed_at`, so the card and the hot-stock rows use one convention. It is split across two rows, because the direction card is only half a card wide: the ticker count and the record count sit on the header row beside the direction swatch, joined by a generated separator, and the latest trade date and the filing date each take a line of their own. Do not put the two dates back on one line — at half width they wrap, and the boundary between them disappears exactly when it matters. Every segment is separately non-wrapping, so no segment may be cut mid-way: those two dates are the card's payload and must stay whole and visibly distinct. Show `people[].role` as an explicit position label only when it has a valid value; never infer a position from party, chamber, or name recognition. The whole card is still the person-detail click target for the mouse — a click on its empty area opens the profile — but that affordance now lives on the card's click listener rather than on the element's identity, so the `aria-label` and the pointer/hover affordance must stay on the name button, which is the keyboard path to the same destination. Three columns hold down to a 1000px viewport; below that the grid drops to two columns, and below 620px to one. Priority and display order come from configured stable IDs. A local demo may instead display `demo_priority_rank` and `demo_priority_group` fixtures, which never enter aggregates or answers; `demo_priority_count` is validation-only fixture data with no UI outlet |
| 国会山买入共识 (buy consensus) | filtered `transactions[]` + derived `market_moves` | Rendered directly below the priority-card grid, as two blocks — 30-day and 90-day — both on screen at once, the way the tables below them are. Each block ranks tickers by summed `amount_high` over that window's purchase records, sums `amount_low` and `amount_high` independently, and shows the top six. Apply no minimum-buyer gate: a ticker qualifies on amount alone even when one person accounts for all of it, because a threshold hidden inside the aggregation makes an absent ticker impossible to explain from the interface. Each card shows ticker and company, the ticker's window price change, the combined buy range, a unique-buyer count, the three buyers with the largest summed purchase amount for that ticker (portrait, name, position, that person's record count, and their own buy range for this ticker), and a footer with the total record count, the latest trade date, and the filing date, plus a link to the security view. Take the company name from the group's `asset_name`, not from `market_moves`, which carries no company field. Render a missing price change as a dash and leave it uncoloured — a missing value is neither a gain nor a decline — and reuse the board's global positive/negative colour rule instead of giving these cards their own `color` declaration, which would win on source order and paint both directions alike. Root each card at `<article>`, never a whole-card `<button>`: the card contains a link to the security view, and a button inside a button is invalid. The whole card opens the security view — a click on its empty area is picked up by a listener bound to the card — while the avatar-and-name element of each buyer is its own `<button>` carrying `data-person-link` that opens that person's profile, with the buyer's own amount left outside it, since the amount belongs to the security. Keep the card root on `data-consensus-card`, never `data-ticker-link`: the ticker delegation runs in the capture phase and stops propagation, so a card-root `data-ticker-link` would swallow the buyer rows before the person delegation ever saw them and the person profile would become unreachable. The card must give hover feedback (the same lift the priority cards use) or a card that is clickable everywhere reads as static layout, and the buyer row gives its own hover cue on the avatar and the name. Because the buyer's avatar and name now live inside that button, the text selectors must be scoped to `.consensus-person > span` — leaving them on `li > span` silently drops the name's ellipsis and the stacked role line. These blocks are not part of the `国会山热门关注股票` / `标的交易明细` switch and carry no tabs or filters. They must not use the `data-window-block` attribute (use `data-consensus-window`): the masthead's 30/90 control resolves that attribute with a first-match lookup, so reusing it would retarget the control to a consensus block instead of the tables |
| Dashboard view switch | filtered `transactions[]` + derived `market_moves` | Each window block defaults to “国会山热门关注股票”, rendered as a real `<table>`: a `<thead>` whose four columns (股票 / 公司, 关联人物, 买入 / 卖出, 股价涨跌) each carry a sort button, over a `<tbody>` the script fills. Each block keeps its own sort key and direction, the way it keeps its own transaction filters — the two blocks cover different windows, so a shared key would silently overwrite whichever sort the reader set on the other one. Clicking the active column flips direction; clicking a new column resets to descending, except the ticker column which resets to ascending. Rows whose price change is unavailable sort last in both directions, never first: a missing value is neither a gain nor a decline. The row number is the attention rank fixed from the default ordering and must not renumber against the active sort, or sorting by price movement would present the top gainer as “rank one”. Each ticker row combines unique-person avatars, disclosure count, a record-count-based buy/sell bar, market movement, and one detail line per direction. The avatars overlap into a stack and each one opens that person's profile, so the stack must show hover feedback on the avatar itself: draw it as a `box-shadow` on the button, not as the outline the board's other avatars use on their image — the stack needs `overflow: hidden` to clip each square portrait into a circle, and that clip cuts precisely at the image's border box, so an image outline is trimmed away entirely and the hover reads as no change at all. The hovered avatar also needs to be raised above its neighbours, because the negative margin that creates the overlap would otherwise let the next avatar paint over half the ring. Each direction line shows the unique-person count, the record count, the independently summed `amount_low` and `amount_high` for that direction, and the latest record's `transaction_date` and `filed_at` in that direction. These per-direction sums are ranges added separately, never a net inflow, net outflow, or net position change, and the trade date and the filing date must stay visibly distinct. The movement is recalculated per block from that block's own 30- or 90-day transaction-date window, from the first completed EOD close on or after that ticker's earliest transaction date in the window through `price_as_of_date`; the UI shows both endpoint dates and states that this is security movement, not person return. The table stacks below 1150px — earlier than the board's other breakpoints, because the 买入 / 卖出 cell holds a direction label, a record count, an amount range, and two dates on one line — and the header becomes a wrapping bar of the same sort buttons rather than being hidden, since that header is the only sorting entry point on a narrow screen. Do not give the table `min-width: 850px`; that rule belongs to the wide tables that sit inside their own horizontal scroller | Switching to “标的交易明细” replaces that block's table with transaction detail, filtered by that block's own search, direction, and instrument controls, with the record count rendered next to those controls rather than in the window heading, since the count belongs to the filtered table and not to the block. Both blocks render both views at once and toggle by view switch, so a filter or a view change never alters which transactions a window covers. Every price-change figure carries the positive/negative class from its value (green up, red down — the US convention this board was specified with, not the red-up/green-down convention of mainland Chinese markets) and stays uncoloured when no comparable price exists, so a missing value is never rendered as a decline |

| Person trade-detail table | filtered `transactions[]` + `security_market_data[]` | One table per person, replacing the former profile/trades/post-disclosure tabs: the page is a single 交易明细披露 view with the post-disclosure observation directly above it — three aggregate figures lead and the record-by-record evidence follows — because a tab named for the trade detail beside a table named for it is self-contradictory. Columns are 标的, 所有人, 方向, 金额, 交易日, 交易日至今涨跌幅, 申报日, 滞后, 交易类型. The 交易日至今涨跌幅 column is `underlying_return_since_trade` — the security's split-adjusted SIP return from the trade date's close to the market-data cutoff — inserted between the trade date and the filing date so the two date-based figures stay distinguishable: one measures from the trade day, the other from the filing day, and there is no combined date. When no market series covers the trade the value is null: render `—`, leave it uncoloured, and keep the formatter null-safe rather than letting `null.toFixed` throw. The table head must be reachable in the first screen, so the hero above it is compressed on purpose and a later size increase is a regression. Compress the portrait's `min-height` rather than only the name and the summary: the identity column beside the portrait is shorter than the portrait, so the portrait is what actually sets the hero height. Two different floors are in play here and they are not interchangeable; conflating them is how the header-wrap regression returns. Give the table its own `min-width` floor of 760px and do not scale that floor from the column count: that floor is the *horizontal-scroll* floor, and it only has to stop a phone from crushing nine columns. Keeping the headers on one line is a separate requirement with a different number: the nine columns need about 952px of table, so the same table wraps its headers well above 760px. Three rules supply that width. First, the person layout's right column is a fixed 250px rather than a proportional track — the constraint there is a floor, not a preference, and once the main column clears ~952px the leftover width is worth more to the table than to the sidebar. Second, `.person-layout` collapses to one column at 1280px, earlier than the heading grid's 1050px, because a two-column layout cannot supply ~952px to its main column below that width. Third, two width steps narrow the cell padding only — 12px at `max-width: 1011px` and 10px at `max-width: 939px` — which buy back 18px of table for every 1px taken off each of the nine columns' two edges and bring the no-wrap floor down from 1012px to 904px of viewport. Measured in headless Chromium against every row's widest cell, the header stays on one line from 1920px down to 904px and wraps only below that, where nine columns genuinely cannot fit. Narrow the padding rather than the company name's `max-width`: truncating the name is the one lever that hides text (a 110px cap already clips two names), while padding hides nothing. Decide wrap by counting line boxes over the header's text range, never by a height threshold — one wrapped header lifts the whole row to 49px and every unwrapped sibling in that row measures 49px too, so a height test reports all nine as wrapped. Do not add `white-space: nowrap` to the headers: that restores a roughly 70px inner horizontal scroll and brings back the problem it was meant to solve. Keep the header's line breaks even with `text-wrap: balance`, or a header that does wrap drops its last character onto a line of its own |

## Filtering clocks

- **Recent trades and person/ticker windows:** `transaction_date`.
- **Newly published disclosures and activity timeline:** `filed_at`.
- **Snapshot freshness:** `data_cutoff_at` plus each source's `last_checked_at` and `last_successful_sync_at`.
- **Market freshness:** `security_market_data[].as_of_date`, which is the latest completed market session, not the wall-clock request time.

## Date rendering

A date field is already a calendar date in the filing authority's own timezone: `transaction_date` is a bare `YYYY-MM-DD`, and `filed_at` is an offset timestamp such as `2026-09-13T22:16:00-04:00`. Render both from the literal year, month, and day in the string. Do not route them through `new Date()` and a locale formatter, which converts to the viewer's timezone: a US evening filing then displays one day late for an Asia-based viewer, and a bare date displays one day early for a US-based viewer. A displayed trade date or filing date must match the filed record exactly.

## Fail-closed rules

- A production disclosure row with a non-allowlisted `source_id`, missing official HTTPS evidence, or non-`official_matched` status is rejected from the canonical snapshot.
- A market row not explicitly marked `source_id=alpaca_sip_eod`, `feed=sip`, and `adjustment=split` is rejected.
- If price history is missing or does not cover an event, the return is null and excluded from performance statistics.
- Frontend code does not accept precomputed vendor scores or infer position effects from buy/sell direction.
- Production snapshots reject `people[].demo_reference_snapshot` and every `people[].demo_priority_*` field; third-party and review-fixture values are never an API fallback.
