01三条不变式

后面每一节都是这三条的推论。如果某处实现与它们冲突，冲突的那一处是错的。

路径即摘要

一个分片的路径就是它自身内容的 sha256。校验因此不需要任何摘要清单， manifest 也就保持在 3 KB 量级，而不是随语料增长的一份索引。这一条同时免掉了 枚举、api.github.com 和速率限制——读端从手里的键直接推出路径。

只有 manifest 和目录索引可变

除 manifest.json 和每目录的 index.json 之外，每条路径只写一次， 永不重写、永不删除。于是「读到发布中途」这件事在构造上不可能产生混合状态：读者要么 拿到旧 manifest 加上旧分片（它们仍在），要么拿到新 manifest 加上新分片。

写入量与变化量成正比，与语料总量无关

一个文件只有在它的大小被单个实体或小聚合限界时才允许被重写。任何随语料增长的文件都 不得重写。参照实现 hunterhigh/10-top-x-semiconductor-tracker 实测 2.27 GiB / 580 次提交 / 70 天，约每次提交让仓库长 4 MB—— 原因正是它每轮在固定路径重写聚合文件（index.json 3.4 MB、 ticker_map.json 555 KB）。那套失败不能换个常数重演。

02仓库布局

两个分支，同一个仓库。main 只追加、永不 squash；market 是派生的、 可复现、整支替换（见 §10）。

路径可写性说明
manifest.json 可变 唯一可变的元数据文件，目标 ≤4 KiB
people/<h2>/index.json 可变 keyhash → contenthash，≤8 KiB，被 1/256 键空间限界
people/<h2>/<contenthash>.json 不可变 一个人的物化：身份 + 其交易 + 其持仓 + requires
tickers/<h2>/{index,<hash>}.json 不可变 一只标的的物化：交易 + 持仓 + 涉及人物 + requires。只存价格标量，不存序列
market/<h2>/{index,<hash>}.json 不可变 在 market 分支上；单只 ticker 的完整日频序列
board/<hash>.json 不可变 自包含看板包：四个数组一次取全，约 150 KB
status/{last-run,last-success}.json 可变 发布 job 的健康输出。读端不读它，但它在仓库里，所以受同一套纪律约束

<h2> 是 sha256("<class>\x00<规范化键>") 的前两个 hex 字符， 256 个桶。类名是复数（people / tickers / market）， 请求模式是单数（person / ticker）——tickers/AAPL 是路径， ticker 是模式。这个区分在读端有具名常量，别把它们混起来。

tickers 和 market 的键规范化成大写，people 的键原样。

03字节编码

这一条不是风格偏好

路径就是这些字节的 sha256。任何编码差异都会让读端把一个完全合法的分片 判为篡改，整棵暂存树被丢弃。用它，不要自己挑序列化参数。 

json.dumps(value, ensure_ascii=False, sort_keys=True, separators=(",", ":")).encode("utf-8")

同一个值序列化两次必须产生同样的字节。这条对分片、对看板包、对目录索引一律成立。

manifest.json 是唯一例外：它是可变的，没有人对它的字节取哈希。 但为了 diff 可读，建议同样按 key 排序。

04manifest.json

读端每次请求先读它，然后按 schema_version、storage_layout 和 snapshot_id 三道闸逐条校验。

键必填读端怎么用
schema_version必填必须等于 politician-dashboard/v1；不等直接拒绝
storage_layout必填必须等于 hash-sharded-v2。不认识的布局必须拒绝，而不是猜
snapshot_id必填非空字符串。它就是版本令牌，见 §09 第 7 步
generated_at必填这次发布发生的时刻，进 meta.generated_at，是给用户看的两个新鲜度事实之一
data_cutoff_at必填数据到哪儿为止。进 meta.data_cutoff_at，渲染器直接读它
board必填看板包的 digest 本身（64 hex，不是路径）。读端拼成 board/<digest>.json
source_health建议见下方说明——它必须在 manifest 里，不能进内容寻址文件
market_commit建议market 分支发布时的 commit SHA。见 §10，缺了它消费端会与替换竞态
is_demo建议true 的 manifest 在非 demo ref 上一律拒绝
meta建议展示字段：title、subtitle、timezone、default_window_days。读端原样透传

为什么 source_health 必须在 manifest 里

source_health[] 的每一行都带 last_checked_at 和 last_successful_sync_at。它们是每轮都变的运行时间戳，放进一个内容寻址的文件 会让那个文件的 digest 每轮都变——写入放大就从这个缝里长回来。manifest 本来就被允许改变， 所以它住在这里。

两个必须缺席的字段

加了就是回归

没有 fetched_at。快照必须是已发布内容的纯函数。带上逐消费者的 取数时刻，两个读者就不会产出同样的字节，包里的可复现性校验随之失去意义。

没有仓库名或 ref 名。渲染器把整份快照以 const DATA = {…} 内嵌进交付给用户的 HTML，而仓库是私有的——写在那里 等于把基础设施泄露进一个用户会分享出去的文件。仓库名和 ref 走 CLI stdout，只进调用方日志。

05索引与分片

目录索引

people/<h2>/index.json 是「从实体键找到当前分片」的唯一入口， 它只覆盖自己那个桶，因此大小被 1/256 键空间限界。 

{ "shards": { "house:P000197": "9f3c…64hex…a71b" } }

读端先在 shards 里查规范化键，查不到再查原键。键是大写规范化过的 （tickers / market），但两种都放行，所以索引里 用哪种写法都不会让读端找不到。

分片形状

四个类共用一套 section 形状，读端因此只有一条组装路径。

类section 键
people person · transactions · reported_holdings · requires
tickers transactions · reported_holdings · people · requires
market security_market_data
board people · transactions · reported_holdings · security_market_data

person 是单数对象，people 是数组——两者读端都收， 组装时单数那个先入列。

五个规范数组里的 source_health 不在任何分片里，它只走 manifest。 剩下四个就是 board 包的全部内容。

为什么没有 holdings/ 和 filings/ 分片类

持仓是 person-scoped 的，直接搭在 person 和 ticker 分片里，所以没有任何一次请求会混到 重叠区块——组装的拼接按构造就不会重复。原始申报也一样：分片路径本身就是内容哈希， 「证据不可变」已经由路径达成，而读端从不读原始申报。

06依赖声明

每个实体分片自己声明它需要什么："requires": ["market:AAPL", "market:NVDA"]。 这是对参照实现最严重缺陷的结构性修复——它把追踪名单抄在四个地方，而且已经漂移。 在这里，「这个页面需要什么」只有唯一真相，且它是生成的，不是手工维护的。

  • 读端只展开 market 类的依赖，扇出受 --max-shards 限界（默认 40）。
  • 超预算的依赖被丢弃而不是报错：一条没有行情序列的记录渲染成不着色的短横线， underlying_return_since_trade 为 null。页面可见地变薄，绝不会给出错误数字。
  • 格式必须严格是 "<class>:<key>"，不能有空格。格式错误读端直接拒绝。
发布方的责任

你发布了实体却没发布它声明的依赖，读端会 fail closed 并点名缺失的键。 依赖完整性是发布前必须自检的一项，不是读端的问题。

07请求成本

这就是「比下载整仓 zipball 可扩展」的依据。读端先读 manifest，那次读取本身就是 新鲜度检查：snapshot_id 与缓存一致时，已发布的语料可证明没有变化， 此后一个字节都不再取。

mode请求数构成
dashboard 2 manifest + 看板包
search 2 manifest + 看板包。任意表达式不指向任何键，无法扇出
ticker X 5 manifest、ticker index + 分片、market index + 分片
person P ≤ 2 + 2 × max-shards manifest、person index + 分片，然后每个 market 依赖两次

每个 market 分片花两次请求，因为要先读它所在目录的 index.json 才知道当前 digest 是哪个。这一层间接正是「某只股票当天价格变了」不会导致每一个持有它的 person 分片被重写的原因——被重写的是那个索引，而它被限界在 1/256 的键空间里。

语料涨十倍，dashboard 的请求数还是 2。这是本次改造的全部意义。

08读端会拒绝什么

下面每一条都是硬失败：报错、点名那个路径或键、整棵暂存树丢弃。没有任何一条会降级成 「用旧数据凑合」。

  • manifest 缺任何一个必填键，或 schema_version / storage_layout 对不上。
  • 分片的字节与其路径里的摘要不符——路径即摘要校验失败。
  • 被点名的路径返回 404。发布是原子的一次提交，所以这只会来自发布方写漏了文件。
  • 已取回的分片声明的 requires 有缺，或格式不是 class:key。
  • 交易或持仓行引用的 person_id 没有对应的已发布人物分片。
  • is_demo: true 的 manifest 出现在非 demo ref 上。
  • 组装的 payload 过不了 process_snapshot.build_snapshot——来源白名单、 official_matched 且带 HTTPS source_url、金额区间必填、 adjustment=="split" 且序列唯一递增、非 demo 时拒绝 demo 字段。
绝不存在的路径

读端没有任何一条代码路径会打开随包发布的演示数据。发布失败时它报错， 不会退回一份样例——把演示数据当作某次失败发布的内容报给用户，是这个包唯一不能有的失败。

09每轮发布序列

一个仓库、一个 workflow、一个 job。参照实现的四 job 矩阵是为了在 BASE_SHA 握手后面协调一个 2.27 GiB 的矩阵构建；写入集只有几十个小文件时 完全不需要。

  1. 读分支尖端的 manifest；跳过年龄门未到的来源。 没有来源到期就直接跳到第 7 步。
  2. 加锁：concurrency: {group: publish-snapshot, cancel-in-progress: false}， 并把 run_id 写进 status/last-run.json，发布时再校验一次。 只有一个触发器时，「重复写入者」问题不存在——这正是参照实现禁用 schedule 要解决的那个问题。
  3. 采集 → 解析 → 规范化 → 只留 official_matched、有 HTTPS source_url、有明确金额区间的行。
  4. 行情：仅当存在新完成的交易日才取。feed=sip、timeframe=1Day、 adjustment=split。
  5. 发布前用同一份 process_snapshot.py 跑 build_snapshot + validate_snapshot。 生产者无法发布一个消费端会拒绝的快照。把 processor_sha256 写进 manifest 作为告警级漂移检测——不一致时消费端照常出数据，只在日志和 meta 里标出来，不阻塞发布。
  6. 建分片 → 算内容哈希 → 写各目录索引 → 写 manifest → 算 snapshot_id。
  7. 空跑短路：新的 snapshot_id 等于尖端值时， 不写任何东西、不提交、直接退出。 这是让节假日和安静时段免费的那一步，也是证明膨胀机制已死的唯一断言。写不动它就等于没改。
  8. 原子发布：git fetch 后断言 HEAD == BASE_SHA，不符则写 status/PUBLISH_CONFLICT.json、不推送、非零退出；然后 git add + 一次提交（snapshot <id> <generated_at>）+ push； 非快进则重解析 base 重试一次。
  9. 健康另记。status/last-run.json、status/last-success.json， 另加 Actions job summary 和上传的 artifact。 仅在状态变化时 + 每日一次心跳提交，所以健康本身不会变成每年 2,920 次提交的洪流，约 5 MB/年封顶。
snapshot_id 的硬性要求

它必须是已发布内容的一个纯函数，且内容没变时必须逐位相同——第 7 步的短路完全建立在 这一条上。推荐做法是对「storage_layout + board digest + 各目录索引的排序键值对」取 sha256，也就是直接拿这棵默克尔树的根。 不要掺进时间戳、run_id 或轮次号。

失败保证是结构性的

发布 = 一次提交一棵树。推送前任何一步失败，上一版 manifest.json 仍在尖端， 而它点名的每条路径都不可变且永不删除，因此那份 manifest 永远自洽—— 没有部分状态要回滚，也没有修复路径可以写错。

触发器

原型阶段用 workflow_dispatch 手动触发就够。转正时用 schedule: "17 */3 * * *"（避开整点拥堵）+ workflow_dispatch + concurrency，用 GitHub 自己的 token（permissions: contents: write）， 不需要 PAT。

  • GitHub cron 在高负载时会延迟 5–30 分钟甚至更多。在 45 天法定申报滞后面前无所谓， 但 manifest 绝不能声称下次运行时间。
  • 计划型 workflow 在仓库 60 天无活动后被禁用。这个 job 会提交，提交就是活动，自我维持。 反过来说：空跑不提交的 job 有可能静默停摆——这正是每日心跳存在的理由，应该写成注释， 而不是让它看起来像冗余。

10market 分支

日频价格序列是唯一「每个实体每个交易日当前值都在变」的内容，没有布局能绕开：任何 「始终最新」的按 ticker 物化都代价约（universe × 单只字节）/ 交易日。物化后约 3,000 只 × 12 KB ≈ 36 MB/交易日 ≈ 9 GB/年。

已决定的方案：market 分支走单条孤立提交、每交易日整支替换， 可达体积恒为当前约 36 MB；旧提交变成不可达，由 GitHub 惰性回收（不保证及时， 这是要接受的事实）。分支若涨得不舒服，删掉重建即可——它可以从数据源一轮复现。

配套纪律，两条都不能少

发布方必须把该次发布的 commit SHA 写进 manifest 的 market_commit。

消费端必须固定那个 SHA 取数，绝不按分支名读——替换与读取之间有真实竞态， 固定到 SHA 即消除。按 SHA 取数还能被 CDN 永久缓存，重复取同一 SHA 是免费的。

11交接边界

已经做完、且已冻结的

  • 消费端全部改造：scripts/snapshot_repo.py（布局、传输、计划、校验、组装） 与重写后的 scripts/fetch_snapshot.py。
  • 契约测试 57 项全绿，其中 tests/test_fetch_snapshot.py 里的 Publisher 类是本契约的可执行形式——它把规范数组变成一棵真实仓库， 读端再读回来。它刻意不签入成静态 fixture，所以两边不可能漂移：任何只有一边知道的布局变更会立刻失败。
  • 差分测试：同一批规范数组，直接 build_snapshot 与走完整管线，输出逐字节相同。
  • 只读代理 GET /v1/<ref>/<path> 的契约已经固定：它把仓库路径一对一映射成 URL， 不持有任何采集逻辑。

上线前的阻塞项

不是本轮工作，但必须留档

Alpaca SIP 再分发是硬阻塞。Alpaca 官方支持页原文： “Unfortunately, you cannot redistribute Alpaca API data.” 无例外、无条件、无授权联系路径；T&C 相应口径为内容 “provided exclusively for personal and noncommercial access and use”。 只读代理把 SIP 派生价格发给终端用户即构成再分发。默认答案是不行， 要走通只能拿到 Alpaca 书面同意。查证已完成，谈判与条款接受需由运营方或法务出面。

官方源商用限制。House Clerk 公开检索页带法定限制，排除新闻媒体以外的 商业使用；Senate eFD / OGE 可能需确认声明或 Form 201 申请。原型阶段已决定搁置， 上线前必须由运营方复核门户条款。data-sources.md 明令禁止自动化确认声明、 冒充用户、提交 Form 201 或绕过访问控制。
