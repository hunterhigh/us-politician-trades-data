## 2. 目标：从官方增量到该前端实际可见

```text
官方目录与原件（evidence）
  → 来源状态、抽取、资格、隔离（state / review）
  → 三源同版候选 + 截止审计（review）
  → 保留旧正式 ID 的五数组候选 + 固定行情（main / market 的准备提交）
  → 最新 HTML 的实际处理器和页面路径验收
  → 唯一完整发布工作流原子移动正式指针、固定提交回读
```

这里有**两个不同的完成点**。第一，恢复当前旧生产路径，使本次合格披露增量进入正式 `main`，同时不丢失旧正式事实。第二，把旧正式事实和该增量按 PR #110 的 G0–G4 路线纳入 vNext 账本/投影，证明新流水线也能生成符合最新 HTML 的完整快照。只完成第一点叫“生产增量恢复”，不叫“流水线重构完成”；只完成影子账本或单个来源解析，也不叫“前端交付”。

最新 HTML 的验证不能只核对交易数量。必须固定候选、`market` 与 HTML 样本版本，用真实候选生成该 HTML 所需的处理后数据，运行其页面脚本与浏览器路径：看板和近 30 日披露窗口按 `filed_at`，其余 30/90 日交易视图按 `transaction_date`；人物、股票、搜索、证据入口能到达新增记录；五数组字段、人物/证券关联、来源健康、缺行情、未知 ticker/持有人、无记录与无窗口记录语义正确。特别核对这四条 House 交易：Pelosi 无 ticker 仍可在人物和披露记录中出现，不被误写为无交易；Rulli 的 GS、MSFT、WFC 按方向和日期进入相应人物/股票路径。原件、审核或无价状态不能被显示成零收益或编造价格。7 个既定收益值为 `null` 并显示“—”，其他有完整历史的收益不能因此被清空。

**现有门禁的具体缺口：** `frontend-e2e/tests/production.e2e.mjs` 读取的是生产构建器调用旧 `render_dashboard` 生成的页面。它已有价值，但不能代替对 `politician-disclosures (3).html` 的验收。R4 必须新增只用于测试的确定性适配：校验原 HTML 哈希，按该 HTML 实际 `DATA` 形状从同一固定候选及行情生成处理后载荷，只替换临时副本中的内嵌数据，不修改原 HTML；随后在此临时副本上执行上述实际页面交互和字段/空值断言。若现有处理器无法生成其必需字段，应修复后端投影并复验。该门禁要接入正式指针移动之前，并对准备提交的固定版本读回再次执行；旧渲染器测试保留作兼容检查。

原 HTML 为 68,817,061 字节，其中内嵌 `DATA` 约 68.6 百万个字符，页面其余代码约 23 万字符；GitHub Actions 不能读取本机 `Downloads`。实施时应从哈希已核对的原文件**确定性提取测试模板**，只把 `DATA` 换成占位符并证明其余字节与原文件一致，保存模板、生成脚本及原文件/模板哈希供 CI 使用。不能只在本机临时打开原 HTML 就声称生产工作流已有该门禁，也不应把整份旧数据随 68 MB HTML 反复提交为生产输入。若模板不能证明与指定 HTML 的页面代码相同，R4 停止放行。

## 4. 偏移处理：先定位失效前提，再决定路径

| 偏移 | 立即处置 | 重新放行条件 |
|---|---|---|
| 另一线程已更新 `code`、G1/G2 产物或生产指针 | 暂停依赖旧 SHA 的步骤，重新固定输入并做逐 ID/字段差异；保留双方工作树改动。 | 新的共同基线与共享文件所有权明确，本计划只补尚缺的事故部分。 |

| OGE 外部响应超时、429/5xx、非 JSON 或页面变更 | 记录原响应元信息，保持上次成功水位；暂态有界重试，结构/许可变化独立核验。 | 官方目录和新增项完整性通过；不能把旧目录、空响应或 HTML 标成新成功。 |

## 5. 如何执行和维护本计划

1. **开工**：先读本计划第 1 节、PR #110 与 #111 的现行方案、最新目标/状态，再跑 R0。不要按旧主工作树的“尚未实施”文档派工。计划中的历史数值只作比较起点。
2. **每个步骤**：记录固定输入 SHA、代码版本、运行命令或 Actions URL、预期与实际、输出 SHA、真实测试结果、未闭合差异。只有达到表中放行件才勾选完成；失败按第 4 节回到相关步骤。
3. **生产写入前**：再次检查六分支、运行队列和另一线程的共享文件/候选进度；如果变了，更新 R0 基线后重算差异。原件仅受控工作流写 `evidence`，`review-input/` 不改，demo 不入正式分支。
4. **两个检查点分别汇报**：R4 汇报“当前生产增量是否恢复”；R5/G4 汇报“新治理流水线是否已能给最新 HTML 供数”。任一未完成都要明确停点，不能把计划、影子审计或手动成功写成正式交付。
5. **收尾**：将实际运行和剩余问题更新至远端 `code` 的[实现状态与下一步](https://github.com/hunterhigh/us-politician-trades-data/blob/code/docs/实现状态与下一步.md)，并把本计划标为完成、部分完成或由新版取代；只记录本次实际运行过的测试。

执行记录最小格式：`时间与时区｜步骤状态｜六分支与 HTML 哈希｜预期→实际｜run/测试/输出 SHA｜偏移与处置｜下一步及重审条件`。同一事件应有一个权威执行记录，避免主工作区旧文档、另一线程计划和本计划形成互相矛盾的三份“当前状态”。
