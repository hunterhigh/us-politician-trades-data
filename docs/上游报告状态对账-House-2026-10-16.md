## 与正式 `main` 的对应和无法推出的结论

固定 `review` 资格件汇合得到 3,755 个唯一正式交易 ID，涉及 364 个有交易的 `filing_id`；`review` House 候选也是 3,755 行。固定 `main` board 中 `source_id=house_clerk` 的交易同为 3,755 行、364 个 `filing_id`。两边交易 ID 集合差集均为 **0**；House 候选与正式 board 中相同 ID 的完整交易 JSON 字段比较也为 **0 项差异**。正式 `filing_id` 均能在固定 `evidence` 的 2026 归档报告中找到。这里没有发现疑似已发布 House 交易无来源报告的问题。

这个一致性只证明被比较的**当前内容**相同，不证明两个固定分支的生成时间、资格输入或发布过程完全相同；本轮没有把 `review` 的较晚状态倒填为 `main` 当时的处理状态。四份明确零交易报告不会出现于 board 的交易 `filing_id` 集合，属于预期差集。2025 的 515 份也不应被简单写成“正式交易遗漏”，应先确定产品承诺的来源年份范围。

## 复算方法和下一步接口

1. 对上述固定 `evidence`／`review`／`main` 提交使用 `git ls-tree -r` 列路径，并按 `git cat-file` 的 blob SHA 读取；本地部分克隆缺对象时，GitHub Git blob API 以同一对象 SHA 回读并核对长度／SHA。不要读取移动中的分支名再和固定结果混用。
2. 各年选 `house_clerk/index/<year>/*.json` 里 `retrieved_at` 最新的归档索引，读取其同 SHA ZIP 的 XML，仅计 `FilingType=P`，按 `(year, DocID)` 去重。原件和四类处理件分别提取路径中的 `(year, document_id, sha)`，做集合差、交集。目录与原件的比较先以 `(year, document_id)` 做，版本分析再加 SHA。
3. 逐件资格读取 `transactions`、`quarantined`、`qualification.zero_transaction_document_count`，使用上表互斥分类；合格／隔离报告的交集单独计算。资格行用 `id` 与 `main` House 交易对应，不能用行数与报告数相减。正式候选和 board 可按同 ID 的 JSON 比较字段。
4. 状态契约应携带 `coverage_years` 或等效范围说明，并把“当前年目录已归档”和“历史目录已发现但未纳入本轮处理”分开。若要把 2025 的 515 份转为实际补采任务，先明确范围和顺序；本对账不自动改变现有采集计划。

本轮没有发现需撤回正式 House 事实的证据；也没有资格规则调整或新增发布。历史范围定义需要主线在 A2 收口，不能由 House 子任务自行承诺全历史覆盖。
