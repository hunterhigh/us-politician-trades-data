## 建议，尚非决定

1. 先修 Senate 年报产物与 PTR 候选契约不一致，恢复定时成功、共同截止推进，再评价调度。若把“名册兼容”改为规范化成员内容摘要，并把原件 SHA 仅用于追溯，则能保留真实成员变更校验，同时避免仅 `<last_updated>` 变化引发全局失败；修改前需补相同成员/不同原件哈希与真实成员变化两类测试。应保留失败可见性；不可用降低频率代替修复。
2. 对 House/Senate/OGE 三个每 6 小时检查做 2–4 周的“运行次数、目标新增、失败、耗时、距正式发布的延迟”记录。若来源目标新增持续稀少且可接受最坏约 24 小时发现延迟，可考虑各改为每日一次、错峰运行并保留维护者手动补采：三者合计计划启动由每周 84 次降至 21 次，减少 63 次（75%）。这是按 cron 算出的启动数差，不是已测省费或已批准时效承诺。年度/白宫专项任务应按自身季节性与覆盖目标单独评估；交易日行情发布不能因为披露源较慢就自动改为周更。
3. 可优先做发布引用的可达性审计，考虑让 `market` 当前分支尖端只保留当前市场页、`main` 尖端只保留当前看板，并验证旧固定 commit/tag 的读取与回退仍正常。理论上可使当前分支树少约 2.26 GB 原始 blob 字节，但正常提交删除不会抹除 Git 历史对象，也不等于仓库磁盘立刻减少相同数额。不得删除已发布标签或其可恢复对象来凑容量。
4. `review` 的旧派生检查点和重复候选仅在证明可从官方原件、确定解析器版本、身份映射与审计状态重建后，才提出保留期与压缩/退役方案。官方 `evidence` 原件、`state` 检查点和未解决隔离记录目前不列入清除项。
5. 旧 bootstrap 发布 workflow 已带“正式快照存在则拒绝降级”保护，故不是当前主要事故根因；后续可停用以减少操作面。9 月 21 日文档中 `bootstrap_empty`、密钥缺失等静态陈述需归位为历史，避免协作误判；其他线程正在编辑这些文件，本次不覆盖。
6. 把三类版本物区分处理：当前清单与主/行情配对提交必须保留；受保护发布标签先做可达性与回退验证；分支尖端旧内容文件可在验证后停止累积。成功发布会原子删除临时 preflight 分支，但失败可能留下残余，宜单独核验。停止当前分支尖端累积可减浅克隆/工作树负担，不直接减少当前读者已经只取 50 页和 1 个 board 的请求量，也不等于 Git 历史立刻瘦身。
7. 固定原件重放工作流若已完成、可由通用解析重建且没有未决覆盖，可停用并归档运行说明；通用候选重建工作流仍有灾难恢复用途。生产代码内的特朗普固定例外需先改为来源绑定的通用例外表或等价规则，并验证 person ID、交易 ID、隔离和前端读回不变，再退役旧分支。仅删文件不能解决当下 Senate 故障或完整 dashboard 的大 JSON 读回。
