# 政客交易 Skill 轻量架构建议

日期：2026-09-18  
用途：供双方讨论的架构调整建议；尚未实施，需双方确认更新时效及接口调整。  
目标：保留现有看板、人物查询、股票查询和数据证据要求，减少首版运行复杂度与潜在成本。

现有设计对按需刷新、数据一致性和历史追溯考虑得比较完整。结合首版的实际使用方式，我们建议优先采用已经在“10 大 V 半导体追踪”项目使用过的思路：**后台统一采集与处理，生成版本化数据快照，Skill 读取快照后生成报告。**

调整重点是数据更新方式与运行部署，不是降低数据质量，也不是重做前端。代价是用户查询时不再保证马上检查官方来源；这个取舍需要明确写进双方约定。

## 1. 两种方案的核心区别

现有要求及据此设计的后端：

```text
用户查询 → Skill → 在线 POST 接口
                      ├─ 检查数据年龄、判断是否需要刷新
                      ├─ 协调采集、解析、数据库提交
                      └─ 返回新快照或回退到旧快照
```

建议的轻量方案：

```text
定时 / 维护者手动启动
        ↓
GitHub Actions：采集 → 解析 → 去重 → 校验
        ↓
保存原件与版本化数据 → 发布完整快照 → 更新 latest 指针
                                            ↑
用户查询 → Skill → 下载已发布快照 → 本地查询 / 渲染报告
```

**每次使用 Skill 仍需要下载数据，但用户查询不再启动采集任务。** 多位用户共享同一批已经验证的数据，查询量与采集次数分开增长。

## 2. 按几个维度比较

| 维度 | 现有按需服务方案 | 建议的定时快照方案 | 主要取舍 |
|---|---|---|---|
| 业务架构 | 每次查询检查刷新条件；“最新/今天”等请求强制检查上游 | 按计划更新，用户读取最近成功发布的数据 | 放弃请求级上游刷新，明确展示截止时间 |
| 数据架构 | PostgreSQL 管规范事实、任务、租约、审计和快照指针，原件另存 | 版本化规范记录、原件、清单和完整 JSON 快照；单一批处理写入 | 首版不依赖在线数据库；复杂检索与大量并发写入能力较弱 |
| 系统架构 | API、采集 worker、数据库、对象存储；有锁、重试、超时和回退协调 | 一个批处理流程，加文件分发；私有访问时加一个只读入口 | 删除请求路径中的采集与数据库事务，仍保留发布校验和失败回退 |
| 物理架构 | 需要后端运行环境、数据库运行环境和文件存储 | GitHub 执行批处理，文件存储承载数据，可选轻量 HTTPS 入口 | 无须常驻 Python 服务和托管 PostgreSQL；并非完全没有云资源 |
| 报告速度 | 命中缓存快；刷新时受官方网站、解析和客户端超时影响 | 下载完成即可本地处理，不等现场采集 | 响应更可预测；大快照的下载和渲染仍需测量 |
| 测试复杂度 | 还要测并发刷新、租约失效、请求超时、数据库事务与恢复 | 重点测采集正确性、完整发布、旧版回退和原版渲染链路 | 来源正确性测试不能省，运行时并发测试显著减少 |
| 维护体系 | 服务可用性、数据库升级备份、连接、任务恢复、来源变化 | 来源变化、定时任务、快照时效、文件备份和发布恢复 | 运维对象更少，但不是无人维护 |
| 版本与 fork | 代码、数据库迁移、服务部署、数据版本需要协同 | 代码版本、数据格式版本、快照版本分别固定和回退 | 无在线数据库迁移负担；格式变更仍需端到端测试 |
| 成本 | 服务和数据库可能有持续费用，采集另占资源 | 主要是 Actions 执行、文件存储、下载及可选只读入口 | 更容易控制成本，但免费额度不是永久零成本保证 |

现有架构并非不合理。如果必须让用户现场检查某个人的最新披露，或未来需要大量个性化订阅和在线写入，它更合适。当前调整是优先解决可维护、可试运行的首版，再根据实际使用扩展。

## 3. 从“10 大 V”项目复用什么

已有仓库 `hunterhigh/10-top-x-semiconductor-tracker` 的已核对模式包括：外部定时触发 GitHub Actions、采集与发布分离、生成 JSON 数据和清单、用确定的版本引用发布结果，以及单独记录运行健康状态。此前核对的主分支提交为 `896a76036f64a17f733aaa70279047be16665356`；这是对已有版本的观察，不代表新项目已经建成。

建议复用：

- 数据提前生成，多位用户共用结果，避免查询时等待抓取。
- 发布结果有版本、有校验，读取方取得同一批数据。
- 采集失败保留上一版，维护者可手动重跑和回退。
- GitHub 管代码、测试、变更评审和运行记录。

建议改进后再复用：

- **不照搬原项目的高频、多 job 矩阵。** 首版使用一个主要采集 job，在内部依次处理少量来源，减少多个 runner 的启动与依赖安装开销。
- 默认使用 GitHub 定时任务，减少外部调度组件；如实测延迟不可接受，再复用原项目的外部定时触发。两者都不承诺准点或上游必然成功。
- 大型 PDF、全量历史快照和行情文件放文件存储，避免长期追加导致 Git 仓库膨胀。Actions cache 和短期 artifact 不作为唯一数据源或长期备份。
- 按来源独立记录成功时间和错误；数据“生成时间”不能代替实际“披露/行情截止时间”。

## 4. 建议的首版部署

建议使用 **GitHub Actions + R2 文件存储 + 一个可选的只读 Worker**。

| 组件 | 首版职责 | 明确不承担的职责 |
|---|---|---|
| GitHub 仓库 | 代码、配置、测试、小型脱敏样本、维护说明 | 不保存令牌，不堆积所有原始 PDF |
| GitHub Actions | 定时或维护者手动采集、处理、验证和发布 | 不因每次用户提问而运行 |
| R2 或等效文件存储 | 原件、规范记录批次、不可变快照、发布清单 | 不作为关系型数据库使用 |
| 只读 Worker（私有分发时推荐） | 检查访问令牌，读取发布清单，返回已发布快照 | 不抓官方站点、不解析 PDF、不运行行情计算、不写规范事实 |
| Skill | 下载同一版本快照，沿用现有处理、查询和 HTML 生成 | 不持有 GitHub 管理令牌或上游 API 密钥 |

如果确认数据允许公开分发，可使用静态 HTTPS 下载入口，省去鉴权 Worker；如果需要私有访问，则保留只读入口，后面的存储桶不公开。不能为了节省 Actions 费用而直接公开原件、行情数据或生产凭据。

这与原来提出的在线后端有实质区别：**即使保留一个 HTTPS 入口，它也只是已发布文件的读取服务，不承担实时刷新和数据库业务。** Worker 仍有用量限制，不能把“轻量”说成没有服务成本。

## 5. 数据结构如何简化，同时保留可信度

首版以版本化文件作为持久化数据，不设置在线 PostgreSQL。规范记录按来源、年份或申报文件组织，以稳定 ID 去重；规模较小时在批处理内加载和合并。确有批处理性能需求时，可使用 SQLite 作为单写者本地工作索引，但它不是 Skill 直接访问的在线数据库，也不作为首版必需组件。

每个成功批次至少保存：

- 官方原件、来源 URL、下载时间、内容哈希及解析版本。
- 规范交易/持仓及其原件关联；修正件关联旧版本，保留历史记录。
- `politician-dashboard/v1` 快照，继续提供 `people`、`transactions`、`reported_holdings`、`security_market_data`、`source_health`。
- 发布清单：`snapshot_id`、代码版本、数据格式版本、内容哈希、覆盖范围、各来源截止时间。

发布时先上传不可变文件，校验成功后再更新唯一 `latest` 指针。全部生产写入走同一个串行发布通道，包括手动补采；发布失败不更新指针。读取方固定快照 ID，不在一次报告中混用不同版本。

初期保留完整的已声明覆盖范围，让现有 HTML 能本地切换人物和股票。快照过大时先测传输、处理及渲染，再设计分片；不能随意只返回某个人的数据，导致原页面跳转后缺失其他内容。

必须保留原来的来源和口径要求：只接纳允许的官方披露来源；行情使用规定的 Alpaca SIP 日线；未知交易金额、未匹配身份和待人工申请文件不能伪造成完整事实；持仓不能靠累计交易推算。人工访问和来源授权问题不会因为换架构而消失。

## 6. 建议对方调整哪些要求

这不是原接口要求的无修改实现，而是一次双方协商的数据交付方式调整。建议把改动集中在取数和时效说明，尽量保留现有展示与统计模块。

| 原要求 | 建议调整 | 涉及位置 |
|---|---|---|
| 每条查询调用 POST，并按年龄门检查上游 | 下载最近成功发布的快照；推荐明确的 GET 快照接口 | `fetch_snapshot.py`、`data-api.md` |
| “最新/今天/刚刚”自动设置 `force_refresh=true` | 解释为读取最新已发布版本，并明确截止时间；用户查询不强制采集 | `SKILL.md`、取数参数、交接说明 |
| 请求中的人物/股票范围决定刷新范围 | 后台按约定覆盖范围统一更新，Skill 本地按问题筛选 | Skill 路由和接口文档；核验原查询脚本的覆盖能力 |
| House 30 分钟、Senate 60 分钟等请求年龄门 | 改为明确的计划更新频率，另设最大可接受陈旧时间 | 来源文档、展示说明、维护配置 |
| 服务在请求中提交数据库后返回新快照 | 批处理验证后发布一个完整、不可变的数据版本 | 后端交接要求 |
| `fresh/fallback` 表示本次上游刷新结果 | 改成描述快照可用性和来源时效，不声称本次请求检查过上游 | 返回元数据、Skill 文案和对应测试 |

如果对方希望暂时保留 POST 调用代码，也可以由只读 Worker 接收原请求并返回快照。但仍必须修改“强制刷新”和时效语义，不能静默忽略 `force_refresh` 并继续声称它已执行。

页面、五类核心数据及本地处理逻辑原则上保留；是否完全不用改 `process_snapshot.py`、`query_snapshot.py`、`render_dashboard.py`，以真实端到端测试为准。不预先承诺零修改或固定开发工时。

## 7. 更新频率和成本控制

建议首版讨论起点为：官方披露索引每天检查 4 次，只下载和解析新增或变化文件；OGE 及名单可按实际变更规律降低频率。美股行情在新完成交易日收盘并经过规定缓冲后更新，结合交易日历处理节假日和夏令时。首次历史回填与日常增量分开执行，并另算预算。

**上述频率是新的产品建议，低于原按需刷新能力，需要对方接受。** 披露并非实时成交数据，但及时发现新公开申报仍有价值，不能据此认定延迟无所谓。

私有仓库的月执行分钟可粗略估算为：

```text
月分钟 ≈ 每日批次数 × 30 × 每批所有 job 的计费分钟之和
         + 测试、行情补充任务、重试及历史回填
```

例如，每天 4 批、每批合计 3–5 分钟，基础采集约为每月 360–600 分钟；这是情景计算，不是已测耗时，也不包含全部任务。首次运行需要测得真实用量再确定频率。账号内多个私有仓库共享额度，不能给新项目单独假定完整的 2,000 分钟可用。[GitHub 计费说明](https://docs.github.com/en/billing/concepts/product-billing/github-actions)

GitHub 定时任务可能延迟，高负载时任务可能被丢弃，因此页面应显示实际成功时间，过期时提示，不能把计划时间当成更新成功时间。[GitHub 定时任务说明](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)

Workers 和 R2 有免费额度，但请求量、CPU、存储及操作次数都有边界。目标应是“先在免费额度内验证，再按实测决定”，不能保证整套长期免费。行情访问和对外分发授权、必要的解析成本也不会因换架构自动消失。[Workers 价格](https://developers.cloudflare.com/workers/platform/pricing/)、[R2 价格](https://developers.cloudflare.com/r2/pricing/)

## 8. 测试、维护与版本纪律

测试保留四条主线：

1. **来源与数据正确性**：真实可使用的官方样本，覆盖修正件、重复记录、缺失金额、身份匹配、持仓口径和行情基准。
2. **完整发布与恢复**：上传中断、校验失败、重跑、重复触发都不损坏当前版本；旧清单可恢复到旧快照。
3. **Skill 端到端**：保留原包 29 项测试作为基线，再测新取数方式到处理、查询和 HTML 生成的完整链路，覆盖 dashboard/person/ticker/search。
4. **时效与性能**：来源失败、计划延迟、快照过期、无可用数据时如实提示；测真实下载、处理和渲染耗时，不只测小样本。

维护入口集中到 GitHub：正常任务输出成功/失败来源、记录变化量和实际截止时间；维护者可手动补采、重放原件及回退版本。批次失败保留旧快照，并单独记录最新运行状态，避免旧快照中的“成功”掩盖最近采集失败。无可用快照时明确不可用，不返回演示数据。

版本上区分代码版本、数据格式版本和快照 ID。代码通过短分支和 PR 迭代，发布绑定已测试的提交；生产凭据只给主仓库的受信任发布流程。Fork 默认不启用生产定时任务、不携带密钥，PR 测试只使用离线样本，不在不可信代码上下文里注入生产权限。格式调整需先验证对方模块，不直接覆盖旧格式数据。

首版不再需要持续维护数据库连接池、在线租约、跨进程刷新锁和请求级采集超时，但仍需文件备份、恢复演练及来源变化处理。私有仓库是否能强制执行保护规则取决于账号套餐；工作纪律不能写成平台已经强制保障。

## 9. 分工与后续扩展

我们负责采集、原件与规范记录、质量校验、版本化发布、读取入口、GitHub 流程及维护说明。对方负责确认可接受时效，调整 Skill 取数和时效描述，并共同验证页面和问答结果。

当实测出现以下需求，再升级为在线数据库和按需服务：必须请求时刷新官方来源；文件快照的体积或本地处理已无法满足体验；出现大量用户自定义订阅或在线写入；单写者批处理不再足够。之前积累的稳定 ID、原件、规范记录和格式版本可以用于迁移，不需要推翻整个前端。

建议先共同确认“定时发布、查询读取”的产品语义，然后做一个完整来源的增量采集和原 Skill 端到端验证，测清耗时、数据量及 Actions 用量，再扩展覆盖范围。该试点用于工程验证，不能包装成已经覆盖全部官方来源的正式产品。

我们的建议是：**首版沿用“10 大 V”项目的批处理和快照交付方式，保留对方现有的数据口径与主要界面，把按需刷新作为后续有实际需求时再启用的能力。** 这样能够减少运行组件、缩短故障排查链路，并让费用更容易估算和控制。
