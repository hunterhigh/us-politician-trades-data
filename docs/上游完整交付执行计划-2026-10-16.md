## 目标、现状和成功边界

目标是让一个固定的 `main` 发布提交同时提供：① 已合格的正式交易；② 对官方已发现报告的可核查处理状态。后者只说明进度，不能进入交易、收益或持仓。消费者读取的是一个固定发布版本，物理上可由清单及其引用的分片组成。数据不变而状态变化时可以有新的 `main` 提交和相同的 `snapshot_id`；不能把 `snapshot_id` 当作整包版本号。

当前正式交易快照可读，`manifest.json` 有时间字段和简要 `source_health`；详细报告状态仍散在 `evidence`、`review`，没有正式的逐报告汇总。`snapshot_id` 的计算不含 `source_health`，`status_revision` 只覆盖现有 `source_health`；完整发布中的行情提交变化仍可能使交易行不变时的 `snapshot_id` 改变。生产清单有 16 KiB 大小上限；公开读取器固定 `main` 提交，读取器对额外清单顶层键较宽容，但不会自动读取新的状态文件。外部实际安装版的行为不能从本仓库推断。当前也没有独立于完整生产工作流的“只更新状态”发布路径。

**完成证据**：固定 `main` 提交能读到交易和状态；状态可从冻结的来源提交逐报告复算；旧正式事实不被状态任务改写；未合格内容不进入交易；同一提交下时间、状态指纹和来源坐标可追踪；生产发布与回读成功；向消费端交付固定版本、数据字典和样例。用户实际页面更新属于双方最终验收，不能由本仓库单方面宣称完成。

### 子 agent 分工与合并门槛

2026-10-16 已让三个子 agent 分别对来源账、发布结构、契约／运维作**只读审查**；上述 A1/A2/A5/A8 的修正来自其文件级检查，由主 agent 复核并写入此计划。子 agent 尚未实施代码、测试或生产部署。

实际实施采用最多三名子 agent 加主 agent 的两波分工，避免四人同时改一个发布器：

| 波次 | 主 agent 负责 | 子 agent 1 | 子 agent 2 | 子 agent 3 | 合并条件 |
|---|---|---|---|---|---|
| 第一波：A0–A3 | 固定共同输入；定义 A2 共享口径和报告账接口；审核三源结果 | House A1-H/A3-H：`(filing_year, document_id)` 报告键、原件哈希版本、部分合格重叠 | Senate A1-S/A3-S：UUID 报告键、修订链、纸表未知格与报告分离 | OGE A1-O/A3-O：全类型目录拆分；直取件有文档 ID，需申请项可能没有，不能套用同一去重键；白宫／OGE 候选去重 | 各源各交冻结坐标、逐报告键集合、差集与未知项；主 agent 不在未闭合时捏造总数。 |
| 第二波：A4–A8 | 锁定统一状态契约、整合差异、核对最新 HTML 语义和生产放行 | 状态生成／发布物：`builder.py`、`materialize.py` 与专属状态目录 | 本仓库读取器、状态哈希／大小校验及新旧版本样例；不修改外部 Skill | 工作流提交范围、固定提交回读、故障恢复与时间／坐标说明 | A4 契约冻结后才并行改不同文件；主 agent 审查跨文件完整性，预发布固定回读和正式门禁全过才发布。 |

后一波若 OGE 资格 B1 更紧急，可在第一波 OGE 账交付后让该子 agent 转做 B1 的只读格式／证据审计；这会替换而不是叠加第二波任务，发布集成仍由主 agent 排序。不要为了用满并发而启动额外工作。

只读核查可以共用当前工作树；实际代码修改各自用隔离工作树／分支，并约定**一个文件只由一个负责人编辑**。主 agent 独占共同状态模型、最终契约、主分支集成和生产发布。子 agent 的提交先独立审查其输入坐标、影响范围和差异，不能凭子 agent 报告直接升级为正式事实。一个子任务失败时只暂停其依赖，不叫其他子任务重复扫描或补写数字。

执行每项任务时使用同一张检查卡：**目标**（是否直接改善上游正式数据或处理状态）、**输入**（是否固定版本）、**事实**（是否把报告、行、交易混淆）、**变化**（是否触动交易门禁、HTML 语义或外部契约）、**退出**（失败能否停在旧正式版）、**授权**（是否越过既有公开来源／部署授权）。检查结果附在任务产物旁；正常实现问题自行修复，触及右列产品决定时先拿具体差异讨论。

**独立工作项 B1（原交接 U1）**：特朗普 2026-09-17 278-T 与 OGE 后续报告沿现有官方版式解析、来源资格和隔离规则处理，给出可发布的正式行或有依据的不予发布结论。其结果更新正式交易，但**不是** A1–A9 状态交付的前置条件；不为赶页面时间单份特批、用目录收录日补申报日，或把 OCR 行直接变交易。解析器能力继续按[官方格式解析重建与隔离率优化方案](官方格式解析重建与隔离率优化方案.md)建设，最后再做统一重放。若该报告仍无法闭合，状态产物应如实显示处理阶段，正式交易保持不变。是否改变资格原则须与用户讨论。

## 推演：遇到问题时如何走

| 场景 | 计划中的处理 | 不能做的事 |
|---|---|---|
| House 一份报告有已发布行和隔离行 | A2 用两个维度记录；A3 同时关联两类行；A4 汇总为“部分合格”，分别报报告数与行数。 | 把整件称为已完成，或把隔离行算作遗漏的正式交易。 |
| OGE 目录已有报告，但原件需申请或申报日未知 | 记录目录收录日、获取障碍和未知申报日；只统计已观察到的目录项。 | 用目录日当申报日，或把未见原件的内容计入交易。 |
| 新状态内容变了，正式交易没变 | 首版随完整发布生成新 `main` 提交和新状态指纹；`snapshot_id` 可能因行情提交变化而变，也可能保持不变。若后续确需状态独立更新再做 A10。 | 只用 `snapshot_id` 判断整个交付没有变化，或声称已有独立状态发布路径。 |
| 一源报告身份重复或状态守恒失败 | A3 隔离该源差异，保留可解释的分项；不发布虚假的统一总数；修源映射后重算。 | 用人工凑数或改交易满足汇总。 |
| 清单超 16 KiB，或外部读取器拒绝新增内容 | A4 用清单引用内容寻址状态件；A6 保留旧正式发布并协商实际升级方式。 | 截断状态或直接把主版本切断。 |
| 状态计算故障但交易候选可用 | 初次切换前保留旧正式版并修状态链；运行期若希望交易仍更新，先由用户确认明确的“状态暂不可用／截止于旧时间”降级规则，再实现。 | 悄悄复用旧状态并标成今日完整，或无决策地让新增状态系统长期阻断交易。 |
| 工作流在预发布检查或最后发布时失败 | A8 不移动正式分支，保留已验证候选和失败证据；按已有恢复路径重建／重试。 | 声称已上线，或留下主分支交易与状态分别来自不同输入。 |
| 特朗普 PDF 继续不能晋级 | B1 保留理由与证据，A 系列状态可准确呈现其处理阶段；继续格式级处理。 | 为了让 OGE 最新日期前进而放松资格。 |

## 决策纪律与执行顺序

常规范围内的公开来源采集、代码修复、只读对账、既有生产发布和验证已经获授权，无须逐步请示。每个任务开工和交付时检查：是否仍服务于同一上游产品、是否改变正式事实或 HTML 语义、输入是否冻结、失败能否停止或恢复、是否引入外部成本／来源限制。普通实现细节由执行者现场决定并记录；当选择会改变产品承诺、资格原则、正式事实、契约主版本或资源授权时，拿具体差异与备选方案同用户讨论。

顺序为 **A0 → A2 最小共同口径＋三源 A1/A3 并行 → A4 契约收口 → 第二波 A5/A6/A7 → A8 → A9**；B1 与状态账独立，A10 在证明确有需要后再议。A4 之前不承诺统一“待审 N 份”；A6 未确认外部兼容前不做破坏性契约切换；A8 不因 B1 尚未完成而等待。私仓可选 `gateway/` 目前不支持新状态路径，当前公开 GitHub 生产不依赖它；不把“所有读取层均兼容”写成完成事实。每一阶段都保留可观察的中间产物和明确停点，避免重扫全部数据或重建消费端页面。
