## 2. 业务用意与实际链路

过去正式交易只能说明“哪些记录可展示”，无法直接回答“官方已看到某份文件，为何页面还没有交易”。新状态交付把这件事补为可消费信息：按范围列出目录发现、原件获取、提取、资格和同版实际发布的关系，能区分未取得原件、提取失败、部分合格、仍隔离、被修订件替代等状态。

工程链路为：**固定 evidence/review + 本轮实际交易候选 → 三源状态适配器 → 逐报告状态输入 → 与准备发布 board 身份核对 → 摘要与内容寻址分页 → 同一 main 清单引用 → 固定提交公开回读 → 现有原子发布**。状态不会调用解析或资格晋级；它读取这些步骤的既有结果。构建器要求每个正式交易 ID 恰好出现在一个报告绑定或明确未绑定集合中，禁止重复／漏记／跨来源归属。当前公开结果中未绑定数为零，但该机制本身允许明确表达未知，而非强造关系。

报告、原件版本、物理格、观察字段和正式交易是不同对象。报告 `record_key/report_id` 与交易 ID 的存在不构成两套冗余正式交易；多个 `source_versions` 是同一报告的原件证据版本。清理任务不能因为它们都像 ID 就删除，也不能把观察格 ID 复制为第二套正式交易 ID。

例：指定特朗普 `Donald-J-Trump.09.17.2026-278T.pdf` 现在可以在正式状态账表达“已归档、已提取、仍隔离、发布交易 0”；目录加入日与未知申报日分开。资格账的 515 个隔离项不是 515 笔已确认交易，也不因状态公开而被晋级。它继续属于原格式任务与 B1 的范围。

## 4. 对执行清单的具体修正

原 T00–T30 的格式优先顺序保持，新增 **T21S：同步适配来源报告状态**，共有 35 个具体行动。它服务于新解析结果与现有交付的连接，不重建状态系统。

- T00/T01：把已上线状态工程和正式清单引用列为现有成果；固定同版来源状态，记录真实 scope，不重复建设或扩大采集。
- T02/T03：加入新／旧提取与资格 schema 的连接、原件哈希／版本绑定、部分合格、当前成功与旧失败并存、未知覆盖／数量和旧版无状态的验收样例。
- T16/T17/T20：把报告身份、原件版本和正式 ID 的对应作为跨层约束；内部迁移映射不能变成双份正式记录。
- T21S：随各源新版产物同步更新 `disclosure_status_house/senate/oge.py` 的读取与状态汇总；主 agent 独占通用状态契约和发布层。标准状态、未知、当前资格与历史观察必须分开。
- T22/T24：逐格式签收同时检查其公开状态解释，逐报告对账正式行、合格行、隔离行、未知页和 scope；旧未知变明确、新恢复或修订引起的状态变化须解释。
- T25：现有交易页面验收继续；状态兼容用本仓库读取器验证，外部呈现只记录实际可核实边界。
- T27/T28：新增状态故障不发布、普通发布不能丢状态、固定提交错版／分页损坏、整包回退、状态变而 snapshot_id 不变的检查。
- T29/T30：清理保护状态链和历史固定版本读取；交付记录同时列交易结果与状态范围，不将状态上线计为格式完成。

## 5. 用户需要知道和可能需要决定的事项

**现在需要知道**：状态交付已能解释处理阶段，但没有新增解析能力；当前正式数据与状态同版，外部页面需要实际消费；6,563 不是待审报告总数；报告状态随完整发布而非实时变化；本次计划需要增加状态适配和回归工作，已有成果可复用，不能推倒重做。

**当前无需重复批准**：同步现有 source scope 内的状态适配、修 schema 连接、增加必要兼容检查和保留恢复路径，属于已授权重构的必要工作；不会因为新增 T21S 暂停无依赖任务。

**确需用户选择时**：希望状态系统故障时仍发布新交易（需定义如何显示缺状态或陈旧状态）；要求独立、更高频状态发布；扩展状态产品覆盖范围或外部显示口径；必须改变正式身份／计数／日期口径。发生这些情况时，先拿实际故障或具体样例、页面影响和选项讨论，不能以本次工程审查为由立刻要求笼统批准。既定 T18/T19 产品决定仍保留。

没有在本轮发现需要立即停运或改写已发布数据的证据。本次是链路与兼容影响审查、48 项针对性测试及固定公开回读，不是对所有源文件事实和未来故障的全面保证。后续实际修改仍按任务门槛验收。
