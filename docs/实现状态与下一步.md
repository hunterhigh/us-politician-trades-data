### Twelve Data 调度与增量更新

- 新证券探索与到期刷新交替处理，单次预算为1时也跨运行交替；某队列为空时另一队列用满预算。刷新按上次尝试时间排序，失败保留旧价格与成功日期，并让其他证券继续获得处理机会。原7天/30天触发间隔及每次100证券上限未改，不把7天理解为全部证券必定刷完的业务承诺。
- 新缓存记录已请求日期范围及完整历史更新时间。普通刷新取45天重叠尾部，重叠价格/日期不一致时立即全取；每30天重新完整取历史。旧缓存无需迁移，新规则首次处理时照常全取并补内部元数据。原价格数组/来源口径继续输出，不能因为做增量就截短报告所需历史。
- 733个真实已发布Twelve Data序列的离线响应回放，在明确模拟已建立缓存元数据的条件下，全取与增量合并结果完全相等；响应价格点从1,203,769降到19,374，按相同JSON响应格式计字节减少98.31%。请求仍为733次，不能把字节减少解释为额度或总耗时减少98.31%。
- 原每次请求固定等待8.5秒，100请求仅等待约14分钟。现在有实际工作时首次查询 `/api_usage` 的 `plan_limit/current_usage`，按已核实额度调节间隔；额度未知则沿用8.5秒，缓存模式零请求。正常每次工作多用1个额度查询credit；账户实际额度在运行日志记录，未提高订阅或购买资源。HTTP/JSON 429均等一分钟再重试。
- 审计和现有工作流日志输出实际额度、等待秒数、响应字节、完整/增量/差异重取数量以及两类积压。缓存复用不再把最后成功同步时间改写为本轮时间。实际账户额度和生产耗时以真实运行结果为准。

额度语义依据：[Twelve Data官方说明](https://support.twelvedata.com/en/articles/5713553-control-over-api-usage)及[官方SDK API usage](https://github.com/twelvedata/twelvedata-node/blob/master/docs/AdvancedApi.md)。

### 披露发布与行情刷新解耦

- `publish-complete.yml` 手动运行默认只发布披露，引用当前正式 main 固定的行情提交，不请求 Alpaca/Twelve Data，也不改 market 分支。需要刷新行情时显式设置 `refresh_market=true`；原 `twelve_data_limit` 只控制刷新任务。
- 行情准备任务使用独立锁，完成后只传递价格、覆盖状态和供应商审计。取得发布锁后重新读取最新 review/evidence/main，重新构建披露；价格任务开始时的旧披露不会覆盖并发新披露。若行情分支本身在准备期间变化，拒绝旧价格交接并明确要求重新刷新。
- 定时开关仍为 `COMPLETE_PUBLICATION_ENABLED`。原工作日22:30 UTC运行改为行情准备；新增22:31 UTC缓存披露发布，二者不在供应商等待期间互相排队。相较原计划，每工作日多一次缓存发布的Actions计算；供应商日预算不增加。发布锁支持排队，仍与bootstrap/rollback共享，价格下载不占此锁。
- 两种模式保留完整价格历史、显式ticker恢复、原HTML头像补充、差异核对、状态绑定、远端回读和页面验收。缓存行情可含当前披露不再引用的证券，人物/证券接口仍只取自身依赖；未价格覆盖的新证券保留披露，收益为null，`coverage.market_missing_ticker_count`真实计数且`market_supported_complete=false`，不伪称不支持或已完整。供应商成功时间不因缓存复用改写。
- 固定生产数据回放及上线运行的实际结果记录在本线程外部治理记录；解析重构路线和v3切换仍由原线程继续。对方合并时需保留其处理器选择，新的缓存HTML命令也应随其原定消费者切换一起采用v3。
