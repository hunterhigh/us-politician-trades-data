# unison 契约适配与数据使用审阅

审阅日期：2026-09-18。依据：用户提供的 `unison-data-contract.html`、已有原版 Skill 包、先前轻量架构建议，以及下列官方资料。

首轮工作是文档和来源条款审阅；此后项目已经建立公开仓库并部署GitHub生产控制面，当前真实实施状态以[当前目标与优先级](当前目标与优先级.md)和[实现状态与下一步](实现状态与下一步.md)为准。至今没有接受Senate/OGE门户声明、自动提交Form 201、联系行情供应商或取得第三方行情再分发授权。HTML 内的实施指令与“已经决定”是对方材料的内容，不视为额外执行授权。

## 结论

新契约采用定时批处理、私有数据仓库、内容寻址分片和只读 Worker，已经承接我们提出的轻量路线；无须回到常驻 Python API + PostgreSQL 的原设计。差异在于它把主要分片存进 Git，并用两个分支区分披露与行情，而此前我们建议用文件存储承载大量数据。

架构方向可以继续，契约中的版本一致性、缓存语义、数据保留和规模断言需要补齐。附件自述读端改造完成、57 项测试通过，但这次没有附新 `snapshot_repo.py`、改版 `fetch_snapshot.py` 和测试代码；本地旧包也没有这些新文件，因此不能确认实际代码已经实现其声称的保证。旧包的29项测试不是新版57项测试的验证证据。

官方披露的新闻媒体例外值得认真评估，但不能仅靠命名或免责声明取得。Alpaca 行情是独立的合同与数据授权问题，即使适用官方披露的媒体例外，也不会自动获得行情再分发权。

## 需要修订或用代码证明的技术点

### 1. 主分支也必须固定读取版本

内容文件不可变，不代表整个多请求读取自动一致。假设客户端先从 `main` 取得旧 manifest，发布随后发生，客户端再从 `main` 取得新的 `people/xx/index.json`，就可能在旧元数据下读取新人物分片。单次 Git 提交的原子性不能跨多个 HTTP 请求延伸。

建议首次解析发布入口时取得确定的主分支 commit SHA，随后 manifest、索引及分片全部按该 SHA 读取；或者将索引也内容寻址，由已固定的发布清单指向它们。主分支 SHA 可由代理响应头提供，避免尝试把自身提交 SHA 写进同一次提交的 manifest。仓库/ref 信息不必进入交付 HTML。

使用市场分支时，`market_commit` 应从“建议”改为必填；先确保市场提交可读取，再发布指向它的主分支清单。两分支不是一次原子事务，需要定义市场先成功、主分支后失败的恢复方式。

### 2. 事实内容与健康状态需要两个更新口径

按契约，`snapshot_id` 只由业务内容生成，而 `source_health` 放在 manifest；空跑时却要求完全不提交。如果没有新交易但检查成功，或者某来源新近失败，状态更新如何到达用户没有闭合。

建议保留稳定的业务内容 ID，另外定义 manifest/health revision。内容不变时不重写分片，但允许节流发布小型健康元数据；客户端必须更新健康与截止信息，不能因业务 ID 相同就直接使用整份旧 payload。缓存标识还需要包含 mode、规范化查询范围及影响组装的配置；同一内容 ID 不代表不同人物请求的结果相同。

运行时间戳不进入实体分片是正确的，但“相同 ID 的整个输出逐字节永远相同”和“相同业务内容下更新来源健康”不能同时不加区分地承诺。建议把复现性定义为固定数据版本、元数据版本、请求范围和处理器版本后的输出一致。

### 3. 256 个桶不是硬性容量上限

平均每桶约为总键数的1/256，并不保证索引永远不超过8 KiB。人物全历史分片、ticker 全历史交易分片，以及包含全部查询数据的 board，也会随时间或覆盖范围增长。哈希地址能复用完全相同的内容，但无法避免“追加一行后重新保存整个历史实体”的增长。

建议先定义首版 universe、查询时间范围、文件大小及传输预算，超过阈值时明确报错或升级布局。后续可按年份/页拆分历史。约150 KB看板与 search 两次请求不能同时当成任意全历史搜索的容量保证：请求次数固定不等于字节数固定；若 board 有限窗口，就必须限制 search 的覆盖并明确提示。

ticker 分片如果包含每日变化的价格标量，仍会每日变化；需列清价格字段与披露事实的分工，否则市场分支分离后主分支仍可能持续大量新增对象。

人物键示例是 `house:P000197`，需要明确自然语言姓名到稳定ID的解析步骤；原包支持姓名文本查询，不能因改成分片而悄悄退化为仅接受ID。依赖应先规范化、去重，再按稳定顺序计入预算，并报告省略的ticker与原因。

### 4. 孤立市场提交不提供长期可重放保证

固定 `market_commit` 可以避免读到另一个版本，但不能保证被强制替换后、失去所有 Git ref 的旧提交永久可取。主分支 JSON 中写入一个 SHA 并不使其成为 Git 对象图的可达引用。缓存也不能代替源数据持久性。

建议选定明确的快照保留期：保留期内用不可变 ref 维持对应市场提交，或把历史市场数据放对象存储，通过代理保持读端接口。保留 ref 会增加真实存储；不能同时承诺历史永远可复现和仓库只保留当天行情体积。

拆股调整与供应商历史修订也使“以后再抓一次”不等价于重现当时的字节。因此应区分可重建当前数据和可重放历史报告。

### 5. 处理后分片哈希不能替代原件证据

分片哈希只能证明分片字节一致，不能证明 PDF 原件或网页原始响应未被改变，也不能恢复未解析、被过滤和被修正的记录。

不必增加读端 filings 分片，但生产侧仍需独立原件归档：原件哈希、官方 URL/申报 ID、下载时间、解析器版本、页码或行号证据、修正关系、未能进入规范数组的原因。原件可放私有文件存储，读端不需要访问。

### 6. 发布并发校验与失败语义需落到可执行测试

`git fetch` 不会自动移动本地 HEAD。只检查 `HEAD == BASE_SHA` 不能证明远端未发生变化；应比较重新读取的远端目标分支 SHA 与原 base，再依靠普通非强推处理竞争，冲突后重新生成/验证结果。workflow concurrency 要覆盖所有写入入口；它不约束其他 workflow、人工推送或其他仓库的写入者。

契约声称全部相关 `requires` 缺失都硬失败，同时允许超过预算的依赖丢弃，需要区分：计划内必需对象缺失/损坏必须失败；预算外有意不加载必须有明确完整性标记。无行情时显示横线只是预期效果，应测试是否影响其他汇总或把缺失错误当作零。

发布失败保持旧版可读，与下载失败时读端拒绝使用本地旧缓存是不同情形；应明确这次契约取消了哪些旧回退保证。processor 哈希不一致仅告警，也意味着两端处理行为仍可能不同，不能声称生产侧验证成功就绝对保证消费端接受。

### 7. 成本与调度文案应更准确

无变化不提交可降低写入和仓库增长，但任务启动、依赖安装和来源检查仍消耗 Actions 执行分钟；“空跑免费”不成立。CDN 命中也不代表代理请求和所有平台资源都不计额度。

每3小时调度只是运行频率，不能承诺House每30分钟或Senate每60分钟检查；后者在附件里应解释为来源最小复查间隔。官方披露自身滞后不代表新公开记录的发现延迟可以忽略，需按产品承诺判断。

附件的“60天无活动禁用计划任务”需要加上公开仓库范围，不能作为私有 `unison-data` 必须心跳提交的依据。健康心跳可以保留，但应以监控需求解释。[GitHub 官方事件说明](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)

## 官方披露：新闻媒体例外如何看

现行法律引用是5 U.S.C. §13107(c)。House和Senate门户仍展示旧编号，但其商业使用限制及新闻传播例外的实质文字一致。OGE也明确列出相同限制。限制涉及取得或使用报告，而不是只限制卖出PDF；JSON化、加代理、私有仓库或免费内测不当然豁免。

- [House 官方检索与使用限制](https://disclosures-clerk.house.gov/FinancialDisclosure/ViewSearch)
- [Senate eFD 使用声明](https://efdsearch.senate.gov/search/home/)
- [OGE 披露使用 FAQ](https://www.oge.gov/web/oge.nsf/publicresources_disclosure-faq)
- [美国法典 §13107](https://uscode.house.gov/view.xhtml?req=granuleid%3AUSC-prelim-title5-section13107&num=0&edition=prelim)

条文确实为新闻与传播媒体向公众传播保留商业用途例外。因此不能简单得出“收费就不行”，也不能得出“做成媒体网页就行”。当前资料没有直接认定本项目属于该例外，必须结合真实运营主体、用途、产品交付方式和收费方式判断。

从产品事实看，下列安排更能支持讨论其新闻传播属性；这是风险分析，不是法定合格清单：

- 实际面向公众持续发布官员财务披露报道、解释与公共监督内容。
- 有明确出版主体、编辑责任、核验、更正和来源说明。
- 清楚区分公开申报、交易日期、披露日期、金额区间及不可推断的信息。
- 以传播和解释披露事实为产品核心，而不是只给少数客户提供批量数据、个性化交易信号或跟单服务。

互动查询和数据图表并不自动排除媒体属性；订阅、广告、免费访问也不能单独决定结果。若实际产品是交易辅助数据服务，仅把名称改成“新闻媒体”、增加新闻栏目或免责声明，不足以证明其使用目的改变。

还应分别审视我们的后台供应方和对方的终端产品。对方主张媒体属性，不代表独立商业数据供应方自动继承该例外。OGE Form 201中的申请者类型为可选统计信息，勾选“News media”并非授权决定；申请应如实填写。[OGE 在线申请说明](https://extapps2.oge.gov/201/Presiden.nsf/201%20Request?Filer=Light&OpenForm=)

建议整理一页真实产品说明和报告样例，列清公众访问方式、收费方式、API/下载、个性化功能、双方身份和原件处理方式，交由熟悉美国政府伦理披露规则的律师评估；向相关披露办公室询问具体访问与使用规则。办公室的答复不应被自动解释为对整个商业模式的全面批准。

## Alpaca：与新闻媒体例外独立处理

Alpaca 官方支持页确实给出默认不能再分发API数据的答复，因此当前普通账号能取数，不足以支持把日线和价格打包发给终端用户。[官方支持页](https://alpaca.markets/support/redistribute-alpaca-api)

但HTML里“无例外、无条件、无授权联系路径”的描述过度绝对。当前官网页脚链接的条款明确规定：对外复制、发布或分发内容需要事先取得Alpaca的明确书面同意；另有用户应用提前30天书面通知要求。通知不是自动授权，书面同意也可能需要涵盖交易所/上游许可。[Alpaca 当前官网链接的条款，第1–2页](https://s3.amazonaws.com/files.alpaca.markets/disclosures/library/TermsAndConditions.pdf)

新闻媒体例外来自官方披露规则，不能覆盖Alpaca合同。延迟行情、收盘日线、付费个人套餐、私有代理、缓存或只展示收益率，均不能据此自动推定获得再分发授权；派生数据范围应按实际许可确认。

联系时应具体列出：SIP日线、历史长度、拆股调整、原始价格还是派生收益、HTML内嵌与可下载性、使用人数与地区、是否收费、缓存保存期及历史版本保留。只询问“API可否商用”不够覆盖实际分发行为。

## 建议的推进顺序

1. 获取与HTML匹配的完整新版消费端、测试及固定版本，补充上述一致性与规模边界测试。
2. 以合成数据验证发布与读取，不把媒体身份成立或数据许可已获批作为隐含前提。
3. 把来源权限与产品用途作为上线前决策，而不是只留一句“合规以后再说”；如拟为商业产品取得官方报告，也应先明确取得用途，而非等对外发布时才判断。
4. 可讨论“披露报道优先、行情可选”的首版。尚未取得行情再分发许可时，行情数组为空、移除其依赖并明确不可用；同样清除披露分片内受限的价格标量/派生字段，验证页面不会把缺失当作零。此改动仍需对方确认和测试，且不替代官方披露用途评估。
5. 将契约结论写成“默认不含第三方数据再分发授权；上线取决于适用用途依据和书面许可”，不承诺媒体身份、许可结果或许可成本。

本审阅用于技术和产品决策，不能替代针对实际运营主体、完整合同和具体商业模式的法律意见。

## 2026-09-20 生产候选补充核验

最新House候选包含81人、3083笔自动合格交易；完整board约1.93 MB，当前披露数据本身未触及8 MiB上限。19笔官方说明中完整披露条款的期权已保留Call/Put、行权价和到期日；3笔只写期权类型、没有完整价格和到期日的记录进入隔离，未用猜测值填充。真实候选已经通过固定原处理器和原渲染器，但以下事项仍阻止“原前端完整验收”结论：

- 人物和ticker窄分片被原静态页面用于二次跳转时，可能把局部交易当作全量统计；完整HTML应先使用完整board，窄包只用于明确范围的问答，直到消费端显示并处理`selection_scope`。
- 姓名查询现已能在固定commit的完整board中做唯一精确匹配并解析到稳定ID，真实候选中的“Nancy Pelosi”已解析为`house:P000197`；旧Skill的完整查询表达式、模糊/歧义姓名和搜索闭环仍需随新版消费端验收。
- 空持仓、未启用来源和无行情仍可能被旧页面显示成0或“延迟”，这需要新版消费端证明其未知/未覆盖语义，不能由后台伪造零值解决。
- House官方目录只有申报日期，当前规范字段仍把它锚定为UTC午夜；这只能作为日期级运输值，不能解释为真实申报时刻，24小时统计需要消费契约明确未知时间精度的处理方式。
