十月披露数据已经发布到 GitHub 正式 `main` 数据分支；用户指定的 `politician-disclosures (3).html` 则是一份把九月数据写在文件里的页面样本，打开它不会读取 GitHub。当前生产工作流确实用新数据临时生成页面并执行浏览器验收，但验收成功没有把该页面交付给用户正在调用的 Skill，也没有把这份 HTML 改造成打开时自动更新的网页。这是**消费端交付接线缺口**，不能再称作“前端生产已更新”。

## 2. 现有路径与实际断点

```text
官方披露 → 解析／资格审查 → GitHub main 正式快照 ──┬─→ 当前仓库的只读适配器
                                                  └─→ 生产工作流临时生成 HTML → 浏览器验收

用户打开的旧 HTML ─→ 读取文件内九月 DATA
用户正在调用的 Skill ─→ 实际安装版本和读取路径尚待消费端确认
```

1. [公开 GitHub 读取器](../client/fetch_snapshot.py)已经具备：先固定 `main` 的提交，再下载清单／分片，核对内容哈希，经过处理器输出页面数据。[使用说明](../client/README.md)给出手动读取和渲染命令。**具备读取器不等于 Skill 已调用它。**
2. `review-input/us-politician-trades-watch/` 是冻结的交接副本。[该副本的 Skill 说明](../review-input/us-politician-trades-watch/SKILL.md)仍要求 `POLITICIAN_DATA_API_URL` 和旧 `/v1/snapshots` 路径；[其取数脚本](../review-input/us-politician-trades-watch/scripts/fetch_snapshot.py)也按该旧接口发请求。**2026-10-16 消费端交接材料对此作出纠正**：它称本机实际安装的 Skill 位于 `C:\Users\admin\.claude\skills\unison`，每次调用均从 GitHub 正式发布读取，并实测取得 18,803 条交易、402 人、截至 2026-10-14 的同一快照。该安装路径在本工作环境不可访问，因此把这条作为消费端实测报告，而非本方独立复验。旧 API 副本不能再当作“实际安装版读旧接口”的证据。
3. [完整生产工作流](../.github/workflows/publish-complete.yml)将处理后的 HTML 放在 runner 的 `$RUNNER_TEMP/complete-dashboard.html`，再执行 `test:production` 和 `test:latest-html`。[后一项检查](../frontend-e2e/tests/latest-html-production.e2e.mjs)取临时 HTML 的 `DATA`，替入用户指定页面的代码，在临时目录用浏览器检查。它是**验收**，不是公开前端部署或 Skill 更新。检查结束后并没有一条已核实的路径把这份临时 HTML 变成用户正在打开的页面。
4. 用户指定的原 HTML 始终是只读基准；`review-input/` 也不直接修改。保护基线本身没有问题，缺少的是一份独立的、使用当前数据的消费端交付物，以及让 Skill 选择它的调用链。

## 3. 前端可能出现的问题

| 问题 | 当前判断 | 用户会看到什么／为什么重要 |
|---|---|---|
| 页面停在九月 | **已确认**：打开原 HTML 只读取内嵌九月 `DATA`。 | 十月正式记录不出现，截止日期和近 30／90 日窗口也以九月为终点。 |
| Skill 实际取数与用户打开的文件未对齐 | **消费端报告称实际 Skill 已读到十月正式快照；本方尚未独立复验其安装物。** 冻结交接副本使用旧 API，但不能代表实际安装版。 | 即使生成时取得十月数据，用户继续打开 Downloads 中的九月样本，仍会看到九月；需要核对 Skill 最终返回的文件路径、字节与用户打开的入口。 |
| 把测试通过当成页面已交付 | **已确认是不同环节**。工作流检查的是 runner 临时页面。 | 发布日志显示页面检查通过，用户拿到的仍可能是旧文件。 |
| 用旧渲染器直接交付 | **需逐页比对**。[交接版渲染器](../review-input/us-politician-trades-watch/scripts/render_dashboard.py)与用户指定的新 HTML 是不同页面代码；不能因数据相同就认定 UI 达到新基准。 | 页面布局、筛选、账户说明、空值等行为可能与用户认可的最新前端不同。 |
| 时间含义混淆 | **已确认有多种时间**：交易日、申报日、数据截止日、各来源最后同步日。 | 用户会误以为“十月收录＝十月交易”或“截止十月＝所有来源完整”。 |
| 未通过资格审查的原件被误展示 | 特朗普目标 PDF **当前尚未进入正式交易**。 | 如果前端自行读 `evidence`／`review` 而非正式快照，会把 OCR 观察或隔离行当作已核验交易。 |
| 缺价／未知值被填成收益数字 | 最新 HTML 验收规则要求无可验证事件日价格的收益显示 `—`。 | 伪造收益或用近似价格会影响交易表现判断。 |
| 页面文件较大、更新成本高 | 用户原 HTML 约 68.8 MB；仅作为当前文件事实，尚未做交付性能测量。 | 每次 Skill 返回完整页面可能慢；可评估传输和缓存，但不能为减小文件而丢失正式数据或改坏页面。 |
| 读取中途遇到新发布 | 固定提交读取器已提供正确边界。 | 若消费端自行从浮动 `main` 分次取文件，可能混用不同版本；应沿用固定提交及哈希校验。 |

## 4. 可选解决路径与建议

| 路径 | 具体做法 | 适用条件与代价 |
|---|---|---|
| **A. Skill 每次调用时生成最新 HTML（建议先做）** | Skill 调用现有 GitHub 只读适配器取得**同一固定提交**的正式快照；用现有处理器得到 `DATA`；把 `DATA` 放进从用户最新 HTML 提取的页面模板；交付新的独立 HTML，并明确显示快照截止、生成时间、提交及各来源状态。 | 最贴合“用 Skill 调出最新前端”；不要求页面打开后联网。每次生成的是新的静态文件，旧文件本身不会自动变化；需要更新实际安装的 Skill／交付入口。 |
| B. 定时发布一个固定网址的页面 | 生产快照发布成功后生成新页面、通过页面验收，再以原子方式切换页面地址；失败时保留上一版并标明日期。 | 适合用户总是打开同一个网址。需要明确托管、缓存、回滚、授权与文件体积；当前仓库没有已核实的此类页面发布链。 |
| C. 浏览器打开时直接读取 GitHub | 把页面改成异步取清单和分片，固定提交、验证哈希、加载状态和失败回退均在浏览器实现。 | 可让同一网页自动看到新版本，但要处理跨域、限流、页面复杂度和 68 MB 级数据加载；属于前端实现变更，不能假定现有 HTML 已具备。 |

**建议顺序：先完成 A，再决定是否需要 B。** A 直接使用现有只读读取器和最新 HTML 模板，能最短路径解决“Skill 仍交旧文件”；B 是面向固定网址的交付选择。C 只有明确要求打开同一页面立即取新数据时再考虑。

## 5. 给消费端负责人的具体交接清单

1. **先定位真实运行物**：消费端已报告本机安装路径与正式快照实测值；仍需提供一次调用最终输出的 HTML 路径、哈希和 `DATA.meta`，与用户实际打开的文件比对。不要用 `review-input` 副本代替实际运行物。
2. **统一取数入口**：按[GitHub 只读适配说明](../client/README.md)固定当前 `main` 提交，读取该提交的 manifest 和数据；核对 `is_demo=false`、内容哈希、`market_commit` 和记录数。失败时明确报告使用的旧版本或停止，不把旧数据标为今天。
3. **保持最新页面代码**：用[已保存的最新 HTML 模板](../frontend-e2e/fixtures/latest-html-template.html)作为页面代码基准，只在唯一 `DATA` 槽放入处理后的正式数据。原始 Downloads 文件及冻结 `review-input/` 均保持不变。交付文件另命名并记录来源提交。
4. **验证实际交付物**：打开**Skill 最终返回给用户的那个文件**，检查截止日期为所读 manifest 的 2026-10-14（以届时真实最新发布为准）、十月交易能在近 30／90 日页面与详情出现、官方链接正确、未知收益显示 `—`，且目标特朗普 PDF 不被误显示为合格交易。检查页面代码和实际数据是否对应同一生成记录。
5. **区分验收与交付**：生产 workflow 的临时浏览器检查继续保留，但增加消费端交付物的来源、生成时间、版本和可达性检查。只有最终文件／网址／Skill 响应确实被用户拿到，才能报告“前端已更新”。

### 完成判据

- 在**用户实际调用的 Skill** 里重新请求 Dashboard，返回的不是 2026-09-27 截止的旧文件；页面展示的截止日期与当时 GitHub `main/manifest.json` 一致，并可追溯到同一个固定提交。
- 可从返回页面打开至少一条已发布的十月交易及其官方原件；同时不把未晋级的 PDF 提取行算进正式交易。
- 页面沿用用户指定 HTML 的实际交互和缺失值语义；30／90 日交易与披露窗口分别按交易日、申报日运行。
- 生成、验收、最终交付三步有同一产物或明确的字节／哈希关联；用户能获得可重复打开的页面，且知道重新调用 Skill 才会生成新版（路径 A）。

## 6. 边界和待核问题

本次独立核查了仓库里的交接副本、适配器、生产工作流、用户指定的本地 HTML 和 GitHub 正式数据；**没有取得用户当前实际安装的 Skill 包、运行日志或它输出的页面**。消费端 2026-10-16 的交接材料已报告其实际安装版成功读取同一十月快照，这推翻了“实际安装版可能仍在调用旧 API”作为当前主因的推测。仍须以第 5 节第 1 项核对最终交付文件与用户打开的入口。

本交接材料描述双方边界；本仓库只承担上游正式数据、状态口径和契约稳定，消费端负责其 Skill 与最终页面交付。用户随后明确将产品层前后端打通置于格式解析重构之前；“先建格式、后统一重放”只保留为新版解析器切换的内部顺序。`evidence` 原件和 `review` 提取结果不能为了让页面变新而绕过正式发布门槛。当前上游顺序以[当前目标与优先级](当前目标与优先级.md)为准。
